# RDC とドメイン

## 1. RDC とは

**RDC = Resource Domain Controller。SoC 内蔵の「アクセス権の関所」ハード。**

i.MX8MM には複数の**バスマスタ**(何かを読み書きしに行く主体)が居る:
A53(Linux)、M4、SDMA、GPU、VPU… これらが共通のペリフェラル(ECSPI2、
GPIO、UART…)にアクセスする。

RDC は各マスタを**ドメイン**に分け、「どのペリフェラルをどのドメインが
読み/書きできるか」を**ハードで強制**する。権限のないアクセスは弾かれ、
i.MX8MM では **SoC リセット**に至ることがある(← 今回のバグの正体)。

この製品でのドメイン割り:
- **domain 0 = A53(Linux)**
- **domain 1 = M4**

## 2. RDC の 2 種類のレジスタ

### MDA(Master Domain Assignment)— マスタをドメインに割り当てる
「M4 というマスタは domain 1」を決める。
```
MDA[M4] = 1   (DID1)
```
実機で `devmem 0x303D0204`(MDA[1])を読むと `0x1` = M4 は domain 1、と確認できた。

### PDAP(Peripheral Domain Access Permission)— ペリフェラルごとの許可
各ペリフェラルについて「どのドメインが読み書きできるか」を 8 bit で持つ。
下位バイトの並び(i.MX8M):
```
bit3=D1R  bit2=D1W  bit1=D0R  bit0=D0W   (D1=M4, D0=A53)
```
- `0x0F` = 1111 = **両ドメイン読み書き可**(A53 も M4 も OK)
- `0x0C` = 1100 = **domain1(M4)だけ読み書き可**(M4 専用、Linux 締め出し)
- `0xFF` = リセット既定(全ドメイン許可、= RDC で特に触っていない)

アドレス = `0x303D0400 + index*4`。実機で読んだ値:

| ペリフェラル | index | アドレス | 既定 ATF | 意味 |
|---|---|---|---|---|
| UART4 | 70 | 0x303D0518 | **0x0C** | M4 専用(だから M4 の UART read は常に安全だった) |
| ECSPI2 | 99 | 0x303D058C | 0xFF | RDC 未設定 = 実は M4 に正式付与されていなかった |
| GPIO3 | 2 | 0x303D0408 | 0xFF | 同上 |
| MU_B | 75 | 0x303D052C | 0xFF | 全ドメイン |

## 3. デバイスツリー(DT)との関係

**直接は無関係。別レイヤー。ただし整合させる必要がある。**

| | 誰が管理 | 何を決める | 効くもの |
|---|---|---|---|
| **RDC** | ATF(ブート最初期) | M4/A53 が**電気的に**触れるか | ハードの強制 |
| **DT** | Linux | Linux が**どのドライバで**どのデバイスを使うか | ソフトの取り決め |

M4 にペリフェラルを渡す時の定石は**両方揃える**:
1. **RDC で M4 に許可**(ATF パッチ)= 電気的に触れるように
2. **Linux DT で `status = "disabled"`** = Linux が同じデバイスを掴んで衝突
   しないように

片方だけだと壊れる:
- RDC 許可だけ → Linux も掴んでダブルマスター衝突
- DT disable だけ → RDC が弾いてリセット(今回の状態)

## 4. なぜ Linux の devmem では RDC を変えられなかったか

ハマったポイント。RDC レジスタ(0x303D0000〜)は Linux から devmem で
**物理的には書ける**(0x0C を書いて読み戻すと 0x0C になる)。**でも効かない**。
理由は 3 つ:

1. **タイミング**: RDC の権限評価は M4 起動やアクセスの時点。Linux が後から
   書いても、M4 のドメイン確定・関門通過には間に合わない。
2. **ロック**: ATF が CSU で RDC 設定を **LOCKED** している
   (`CSU_CSLx(CSU_CSL_RDC, ..., LOCKED)`)。ロック後の変更は無視される。
3. **domain の壁**: M4 自身が RDC を書いても無言で無視される(実験で確認)。
   RDC の設定変更自体が特権操作。

→ **RDC は「ブート最初期に一度だけ、EL3 の ATF が確定させる」もの。**
後から緩められない設計。だから ATF パッチが唯一の正解だった。

## 5. ATF は RDC を「読み込む」? バイナリに埋め込まれている?

**ソースに直書き → バイナリに埋め込み → ブート時に自分でレジスタへ展開。**
外部から読むファイル(DT みたいなもの)ではない。

```
① imx8mm_bl31_setup.c に C 配列で書く:
     static const struct imx_rdc_cfg rdc[] = {
         RDC_MDAn(RDC_MDA_M4, DID1),
         RDC_PDAPn(RDC_PDAP_UART4, D1R | D1W),
         RDC_PDAPn(RDC_PDAP_eCSPI2, D0R|D0W|D1R|D1W),  ← 今回追加した 3 行
         RDC_PDAPn(RDC_PDAP_GPIO3,  D0R|D0W|D1R|D1W),
         RDC_PDAPn(RDC_PDAP_GPIO5,  D0R|D0W|D1R|D1W),
     };
② コンパイル → bl31.bin の定数データに焼き込まれる
③ ブート時、BL31 が imx_rdc_init(rdc) を呼び、この配列を舐めて
   RDC レジスタに書き込む → その後 CSU でロック
```

**変えるにはソースを直して bl31.bin を再ビルドするしかない**(= 今回の ATF
パッチ)。DT のように後から差し替えられない。

## 6. 一枚まとめ

```
RDC = ペリフェラルのアクセス権をハードで強制する関所
  ├ MDA: マスタ→ドメイン割当 (M4 = domain1)
  ├ PDAP: ペリフェラルごとの D0/D1 読み書き許可 (0x0F=両方, 0x0C=M4専用)
  ├ ATF がブート最初期に bl31.bin 内の配列から設定 → CSU でロック
  ├ Linux devmem では実質書けない (タイミング / ロック / domain の壁)
  └ DT とは別物。「RDC で M4 許可(ATF) + DT で Linux から disable」を揃える
```

## 6.5 RDC の隣にもう一つのドメイン関門 — CCGR (クロックゲート)

RDC (アクセス許可) を通しても、M4 のペリフェラル read が SoC リセットを
起こすことがある。第 2 の関門が **CCM の CCGR (クロックゲート)**:

- CCGR はペリフェラルごとに **ドメイン別の要求フィールド** を持つ
  (4bit/domain: bits[3:0]=domain0, bits[7:4]=domain1, …)。クロックは各
  ドメイン要求の OR で回る — が、**「回っているか」と「自分のアクセスが
  受け付けられるか」は別**で、アクセス元ドメインの要求ビットが立って
  いないとバスが応答しない (→ read が stall → SoC 無言リセット。
  RDC 不許可と同じ死に方なので切り分けを誤りやすい)。
- **各ドメインは CCGR の自分のフィールドしか書けない** (実測: Linux
  (domain0) から 0x33 を書くと 0x03 に化ける)。つまり Linux は M4 の分を
  立てられない — **M4 が自分で SET レジスタ (+4) に書く**しかない。
  NXP SDK の `CLOCK_EnableClock` が `SET = 0x3333` (全ドメイン分) を書くのは
  「自分のドメインの分だけ通る」ことを見越した書き方。
- 教訓: **「M4 にペリフェラルを渡す」= ①RDC PDAP (ATF) ②CCGR domain1
  (M4 自身) ③root クロック維持 (Linux 側 mcore_booted=1) の 3 点セット**。
  どれか欠けても「M4 が read した瞬間 SoC リセット」で、症状からは
  区別できない。実測記録: 04-case-study と kmm-yocto pitfalls #26 追記。

## 7. 一般化 — 「マスタ ID ベースのバスファイアウォール」

RDC は特殊な仕組みではなく、**「バスマスタ単位でアクセスを許可/拒否する
SoC のバスファブリック関所」という一般クラスの、NXP 実装**にすぎない。
他ベンダの SoC にも同じ発想の別実装がある(例: バスマスタ ID を Region-ID に
対応づけて、ペリフェラル/メモリ領域ごとに read/write を許可する方式)。
名前もレジスタ配置も違うが、**踏むバグは同型**。

### 共通原理(ここが本質・最重要)

> これらの関所は「**誰がアクセスしたか(バスマスタ ID / ドメイン)**」で弾く。
> 「**どんな特権で(EL0〜EL3、セキュア/非セキュア)**」は無関係。
> だから**特権を上げても(EL3 に行っても)すり抜けられない**。
> 回避するには**関所そのものを設定する**しかない。

- こちらの RDC で「Linux(EL1)の devmem では効かない / M4 自身の書込は無視」
  だったのも、別 SoC で「その firewall は EL 非依存で **EL3 でも弾かれる**」と
  観測されたのも、**同じ性質の別の顔**。マスタ ID で弾く関所は、権限の高さでは
  突破できない。
- 弾かれた時の症状はハード実装依存: **SoC リセット**(i.MX8MM の RDC)か、
  **AXI abort → ハング**(別実装)か。いずれも「静かに死ぬ」ので原因が
  見えにくい。

### ベンダ差(=普遍則ではない部分)

「どの特権レベルから関所を設定変更できるか」「ロックされるか」は**実装依存**:

| 観点 | i.MX8MM の RDC | 他実装の一例 |
|---|---|---|
| 設定できる場所 | **EL3(ATF)独占** | **EL2(U-Boot レベル)から writel 可**な例もある |
| ロック | CSU で LOCKED → 後から不可 | ロックしない例もある |
| 開け方 | bl31.bin を再ビルド | U-Boot でレジスタ書込を足すだけ、で済む例もある |

→ **「関所を触るなら ATF」は i.MX 固有の事情であって、普遍則ではない。**
新しい SoC を触るときは「この SoC のマスタ ID 関所は、どの EL から・
ロック前のどのタイミングで設定するのか」をまず調べる。関所の存在(=マスタ
単位で弾く)は共通、設定方法だけがベンダ差、と捉えると移植が速い。

### デバッグの勘所(SoC 横断で効く)

- あるバスマスタ(サブコア/DMA/別 IP)のアクセスだけが**静かに死ぬ**
  (リセット/ハング、panic 無し)→ **マスタ ID ベースのバスファイアウォールを
  真っ先に疑う**。クロック/電源/権限(EL)より先に。
- 「特権を上げても直らない」「実行時に該当レジスタを書いても効かない」は、
  この関所の典型的な指紋。
