# フレームバッファとブートスプラッシュ

XPI-iMX8MM の起動スプラッシュ最適化(実務記録は
[docs/imx8mm-xpi-bringup/11-splash-optimization.md](../docs/imx8mm-xpi-bringup/11-splash-optimization.md))
で出てきた「なぜ」を、表示の基礎概念として復習用にまとめる。

## 1. フレームバッファ(FB)とは

**FB = メモリ上の「画面 1 枚分の生ピクセル置き場」。** 1 画素 = 4 バイト(XRGB8888 なら
B,G,R,X の順)、1920×792 なら 1920×792×4 ≈ **6MB**。

表示コントローラ(i.MX8MM では **eLCDIF**)は、この FB を**常時 DMA で読み続け**、
1 ラインずつパネル/HDMI にピクセルを流す。だから:

- **FB に書いた内容 = そのまま画面に映る。** 別の「描画命令」は無い。メモリを書き換えるだけ。
- ここでは FB の物理アドレスは `0xBFA00000`(DRAM の上位)。eLCDIF のレジスタに
  この先頭アドレスを教え、RUN ビットを立てるとスキャン(表示)開始。

「画像を表示する」= PNG をデコードして…ではなく、**生ピクセルを FB に置く**だけ。
SPL のスプラッシュも、事前に PNG→生 raw に変換したものを FB に書いているだけで、
SPL 自身は画像デコードをしない。

## 2. なぜ「表示中の FB」への書き込みは激遅なのか(★核心)

素朴には「6MB を DRAM に書くなんて一瞬」のはず。ところが実測 **~4MB/s**(6MB で ~1.4 秒)。
理由は **表示 DMA との帯域競合**:

- eLCDIF は表示のため FB を**毎フレーム丸ごと読む**。
  `1920×792×4 バイト × ~60Hz ≈ **365 MB/s**` を DDR から吸い続けている。
- その最中に CPU が同じ FB へ書き込むと、DDR/NoC の帯域を表示 DMA に食われ、
  さらに「今スキャンしている場所」との整合も要り、CPU 書き込みが**餓死**する。
- 逆に、**スキャン開始(RUN)前**に FB を埋める分にはこの競合が無い(SPL の「全面を背景色で
  塗る fill」は RUN 前なので速い)。

→ 教訓: **表示コントローラがスキャン中の FB に大量書き込みするな。**
書くなら (a) スキャン開始前に、(b) 書く量を減らす、のどちらか。
(スプラッシュ最適化はこの 2 つ:ロゴだけ描く / RUN 前に描く、で ~1.4s を消した。)

## 3. ブートスプラッシュのバトンパス(誰が絵を持っているか)

電源投入直後のロゴを GUI まで途切れず出すのは、「FB の所有権」を段階的に渡すリレー:

```
SPL          : FB(0xBFA00000)にロゴを描く → eLCDIF に表示させる
   │  (ここで電源→最初の絵)
   ▼
カーネル DRM : 通常はパイプラインをリセットして初期化し直す = 一度暗転
   │          → 「養子縁組(seamless takeover)」で、同一モードで駆動中なら
   │            リセットせず引き継ぐ。cur_buf を触らず SPL の FB を出したまま。
   ▼
コンポジタ    : weston が自前の DRM バッファを用意し、ページフリップで
(weston)      cur_buf を自分のバッファへ切替 → ここでロゴが GUI 描画に置き換わる
```

ポイント:
- **カーネルは画像をロードしない。** SPL が置いた FB をそのまま生かすだけ(takeover)。
- `mem=2042M` で FB 領域(上位 6MB)をカーネルの割り当て対象から**隠す**ので、
  SPL の FB が再利用・上書きされない。
- 暗転が起きるのは「誰かが FB をリセット/差し替える瞬間」。takeover はカーネル段の
  リセットを消すが、**コンポジタが自前バッファへフリップする瞬間**は別レイヤ
  (カーネルパッチでは覆えない)。

## 4. データ駆動 vs 手続き描画

ロゴを画面に出す 2 つのやり方:

| | データ駆動 | 手続き描画(procedural)|
|---|---|---|
| ロゴの正体 | 全画素の色を並べた**データ**(生 raw)| ロゴを**生成するコード/圧縮データ**(例:1bit マスク)|
| 置き場所 | 外部ファイル(ここでは FIT loadable)| コード本体に埋め込み |
| 出す方法 | データを FB へ**コピー**(計算ゼロ・量が多い)| コードが画素を**計算して**FB へ書く(量は少・要コード)|

- データ駆動は「運ぶ量」がそのままコスト(§2 の競合下だと致命的)。
- 手続き描画は、例えばロゴを **1bit マスク**(点灯/消灯だけ。純白線画なら劣化なし)として
  数 KB 埋め込み、実行時に「ビットが立った画素だけ白を書く」。運ぶ量がほぼゼロになる。
- 欠点:写真調・グラデには不向き(単色/線画向き)。そして**コード = ブートローダ側**なので
  更新に OTA が効かない(§5)。

## 5. 補足 — 「コードの更新」と「データの更新」は配布経路が違う

同じ「起動画面を変える」でも:
- **データ(FB に載せる画像 = falcon.itb の中)** → OTA で配れる。
- **コード(SPL 本体 = flash.bin)** → OTA は flash.bin を触らないので配れない。
  ブートローダの書き換え(実機なら eMMC 直書き / UUU)が要る。

「何を変えたか」より「**それがコードかデータか、どのイメージに入るか**」で配布経路が決まる、
というのは組込みで頻出の落とし穴。実務手順は `imx8mm-xpi-bench` skill 参照。

## 6. 一枚まとめ

- FB = 生ピクセルのメモリ。表示コントローラが常時 DMA で読んで画面に出す。書けば映る。
- 表示中(スキャン中)の FB への大量書き込みは、表示 DMA の帯域(~365MB/s)に食われて激遅。
- ブート画面は「SPL が描く → カーネルが殺さず引き継ぐ → コンポジタがフリップ」のバトンパス。
- ロゴは「運ぶ(データ)」より「生成する(手続き)」方が軽い。ただしコードは OTA で配れない。

## 7. 一般化 — 「表示帯域」と「バトンパス」(SoC/EL 非依存)

**共通原理(ここが本質):**
- どの SoC の表示コントローラも、FB を**スキャンアウト DMA で読み続ける**。
  そのバンド幅は `解像度 × bpp × リフレッシュレート`。4K@60 なら ~2GB/s にもなる。
  **「表示中の FB へ CPU/別マスタが書くと、この DMA と帯域を奪い合う」**のはどの SoC でも同型
  (i.MX でも、Rockchip でも、Qualcomm でも、PC の GPU でも)。
- **ブート画面の途切れなさ = FB の所有権の受け渡しが滑らかか**、という問題。
  ファーム(SPL/UEFI)→ OS カーネル → コンポジタ、と主体が変わるたびに
  「リセットせず引き継ぐ」か「一度作り直す(暗転)」かの選択がある。Linux の
  simple-framebuffer / DRM の hand-off、これらは全部この「バトンパス」の実装。

**勘所(横断で効く):**
- 起動画面がチラつく/暗転する → 「どの段が FB を作り直しているか」を切り分ける
  (ファーム? カーネル DRM? コンポジタ?)。段ごとに「引き継ぎ」か「作り直し」かが決まる。
- 起動画面の描画が妙に遅い → 「表示スキャンを止める前に描いているか」を疑う。
  スキャン開始後に大量に書いていれば §2 の餓死。
