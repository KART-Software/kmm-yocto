# 01 — Cortex-M7 の起動とプログラムロード(事前リサーチ)

XPI-iMX8MM の M4 で確立した流儀([../imx8mm-xpi-bringup/10-cortex-m4.md](../imx8mm-xpi-bringup/10-cortex-m4.md))
がどこまで持ち込めるかの調査。ソースは Zephyr upstream・NXP カーネル
(work-shared/imx8mp-lpddr4-evk)・debix-tech の公開 U-Boot(https://github.com/debix-tech/uboot-nxp-debix)。
実測は実機到着後にここへ追記する。

## ハード概要(8MM M4 との対比)

| 項目 | 8MM Cortex-M4 | 8MP Cortex-M7 |
|---|---|---|
| コア | ARMv7-M, キャッシュ無し | ARMv7E-M, **I/D キャッシュ付き** |
| 最大クロック | 400MHz(実測で引き上げ済み) | **800MHz** |
| TCM(M コア視点) | TCML 0x1FFE0000 / TCMU 0x20000000 | **ITCM 0x0** / DTCM 0x20000000 |
| TCM(A53 視点) | 0x007E0000 / 0x00800000 | **同じ 0x007E0000 / 0x00800000**(各 128KB) |
| ベクタテーブル | TCML 先頭 | ITCM 先頭(= M7 視点 0x0) |
| リソース分配 | RDC | RDC(同系) |

- A53 視点の TCM アドレスが 8MM と同一なので、SPL/BL31/スクリプト類のアドレス定数はほぼ流用可。
- M7 はキャッシュがあるため、**共有メモリ(vring/rsc_table)は非キャッシュ設定が必須**
  (Zephyr は `soc/nxp/imx/imx8m/m7/mpu_regions.c` で設定済み)。代わりに **DDR 実行が実用的**
  になる(8MM M4 の DDR 実行は遅くて非現実的だった)。

## 起動方法 — 3 経路とも 8MM と同型

**起動の最終段は全経路共通で BL31(ATF)への SIP コール**。
`IMX_SIP_SRC_MCU_START`(0xC2000005)を投げると BL31 が SRC の M7 リセットを外す。
カーネルの imx_rproc も 8MP は `method = IMX_RPROC_SMC`(imx_rproc.c: `fsl,imx8mp-cm7` →
`imx_rproc_cfg_imx8mn` 共用)なので、8MM で作った「BL31 が TCM 起動」の設計はそのまま通る。

1. **U-Boot `bootaux`**(手動デバッグ用)
   - TCM(A53 視点 0x7E0000)にバイナリをロード → `bootaux 0x7e0000`
   - NXP/DEBIX U-Boot に実装あり(arch/arm/mach-imx/imx_bootaux.c、SMC 経由)。
     ただし **DEBIX の defconfig(imx8mp_debix_model_a)では CONFIG_IMX_BOOTAUX 無効** — 有効化が必要。
     u-boot-fslc 側も同様に要 defconfig 確認。
2. **Linux remoteproc**(開発イテレーション用 = 8MM の try.sh フロー)
   - DTS に `imx8mp-cm7` ノード(EVK 例: `imx8mp-evk-rpmsg.dts`。compatible は
     `fsl,imx8mn-cm7` を共用)+ 予約メモリ:
     vdev0vring0/1 @ **0x55000000/0x55008000**、vdevbuffer @ 0x55400000、
     rsc_table @ 0x550ff000(8MM は 0xB8000000 帯だったのでアドレス帯が違う点だけ注意)
   - MU mailbox(`&mu 0/1/3`)、`fsl,startup-delay-ms = <500>`
   - `/sys/class/remoteproc/remoteproc0/{firmware,state}` に ELF 名と start/stop — 8MM と同じ操作
   - **スキャフォールドビルドの deploy に `imx8mp-evk-rpmsg.dtb` が既にある**ので、
     EVK machine のまま remoteproc の動作確認まで可能な見込み
3. **Falcon 統合**(製品用: SPL がファーム検証→ステージング、BL31 起動 — 8MM で確立した方式)
   - 8MM の分離配布設計(m4-fw.img + SPL 検証)の移植。SIP ハンドラが共通なので設計変更不要の見込み

## プログラム(ファームウェア)のロード形式

- **remoteproc 経路 = ELF**(zephyr.elf を /lib/firmware へ。rsc_table を ELF 内に持つ —
  8MM で使った `CONFIG_RAM_CONSOLE` → `fw_rsc_trace`(trace0)の仕掛けはアーキ非依存でそのまま効く)
- **bootaux / SPL 直ロード = raw bin**(zephyr.bin を TCM 配置、ベクタテーブル先頭)

### Zephyr 対応状況(upstream、手元ツリーで確認済み)

- ボード: **`imx8mp_evk/mimx8ml8/m7`**(ITCM リンク、128KB 制約 = 8MM と同じ → can-gw 規模は OK)
  と **`.../m7_ddr`** 変種(サイズ制約なし、キャッシュありで実用速度)
- デフォルトコンソールは **uart4** — 8MM アプリと同じ構成
- クロック init(`soc/nxp/imx/imx8m/m7/soc.c`)は M7 root を SysPll1(= **800MHz)に設定済み**。
  8MM でやった「Zephyr 側 400MHz 化」に相当する作業は不要
- MCUXpresso SDK(MIMX8ML8)の M7 デモも素材として使える

## DEBIX 固有の注意

- **公式 BSP の Linux DTS(debix 系)には cm7/rpmsg ノードが無い**(最小構成)→
  自前 DTS 整備の一環で cm7 ノード + 予約メモリを追加する(EVK の rpmsg DTS が雛形)
- M7 コンソールに使う UART4 は **J2 ヘッダー Pin17=UART4_RXD / Pin19=UART4_TXD** に出ている
  (8MM の J64 と同じベンチ運用ができる。J2 は 2.0mm ピッチ)
- DEBIX からの M7 サンプル配布は BSP クローン内には見当たらない(U-Boot/Linux のみ)

## そもそも M7 に何をさせるか(設計判断、plan #5)

8MP は FlexCAN×2 が A53 ネイティブになるため、8MM で M7(M4)に置いた
**CAN ゲートウェイの役割は消える**。残る候補は ADS8688(SPI ADC)等のリアルタイム収集。
M7 を使わない選択肢も含めて、キャリアボード設計(local/carrier-board-design.md)と合わせて判断する。

## 実測(2026-09-08): remoteproc 経路で can-gw まで動作

構成: `kas/imx8mp-m7.yml`(DT 変種 `imx8mp-debix-m7.dts` = cm7 ノード + 共有メモリ
0x55000000 帯 + flexcan1 を M7 譲渡で disabled、rpmsg-can 同梱(netdev は rpmsgcan0、flexcan2 は can0 のまま)
固定)、ファームは data-logger-zephyr `apps/can-gw` の `imx8mp_evk/mimx8ml8/m7` ビルド
(ITCM リンク、FlexCAN1 直駆動、rpmsg チャネル "rpmsg-can"、RAM console)。
ロードは `/lib/firmware` に ELF を置いて `/sys/class/remoteproc/remoteproc0` から start
(8MM の try.sh と同じ。firmware_class の path パラメータは使わない)。

結果: rpmsg "rpmsg-can" が bind して Linux に rpmsgcan0(rpmsg-can)が生え、`ip link set rpmsgcan0 up`
で M7 が set_bitrate 1M → start。ループバック(`type can loopback on`)で Linux → rpmsg → M7
FlexCAN1 → rpmsg → Linux の往復、実バス(J2 Pin31/33 → CA-IS3050G → CANable の CAN mock)
からの受信(0x5F0〜0x5F4、932 フレーム/5s、M7 側 can→rp カウンタ一致)、kmm が rpmsgcan0 から
値を表示するところまで確認。M7 側ログは `/sys/kernel/debug/remoteproc/remoteproc0/trace0`。

### 落とし穴: M7 ルートクロックは誰も立てない(EVK は U-Boot proper 頼み)

EVK の rpmsg DTS は cm7 の clocks に `IMX8MP_CLK_M7_DIV` を指すが、NXP 6.6 カーネルの clk
ドライバは M7 を composite "m7_core"(`IMX8MP_CLK_M7_CORE`、CCM 0x30388080)でしか登録して
いない。M7_DIV は optional clk として NULL に解決され imx_rproc は何も有効化しないため、
ルートの ENABLE(bit28)が落ちたまま。その状態で remoteproc が ELF を TCM(A53 視点
0x7E0000)へ書きに行くとバスが止まり WDT → PMIC リセット(SRSR は POR のみ、シリアルに
何も出ない)。16 バイトの無限ループでも同じなので firmware は無関係。EVK では U-Boot proper が
起動時に M7 クロックを立てるので無症状、falcon 経路では誰も立てない。
切り分け: `devmem 0x30388080 32 0x11000000` で手動 enable → TCM が読め、start も通る。
修正: DT の clocks を `IMX8MP_CLK_M7_CORE` にする(imx_rproc が probe 時に有効化)。

### メモ

- Zephyr の 8MP M7 SoC init は M7 を RDC domain 1 へ移し、AHB root を一瞬 24MHz に
  切り替えてから SysPll1/6 に戻す(NXP SDK 由来)。Linux 稼働中でも問題は出ていない。
- `imx_rproc_kick: failed (0, err:-62)`(解決、2026-09-11): Linux の kick = MU-A TRn 書きは M7 が
  MU-B RRn を読むまで完了せず、M7 は MU 割込みを使わない方針で誰も読まなかった → tx_tout=100ms
  で諦める。attach 直後の 1 発が root マウント前の `wait_for_device_probe()` に乗って **PID1 が
  0.09s 遅れ、電源→GUI +0.10s**(対照実験で確定、30-boot-time.md 09-11 行)。fix = M7 の 1ms
  ポーリング内で SR.RFn を見て RRn を読み捨てる(data-logger-zephyr 9e4d7aa)。以後 kick failed 0 件、
  PID1 は対照と同じ 0.77s。
- CAN1 の root clock は Linux の flexcan1 が disabled のため Linux は触らない。M7 側
  (Zephyr の ccm ドライバ + main.c の CCGR)で 24MHz osc のまま enable される
  (0x3038a200 = 0x10000000)。pinmux も M7 overlay が当てる(SAI5_RXD1/RXD2 = ALT6)。
- CAN mock(ホスト CANable、`can-mock-py`)は**ボード側の CAN が消える(リブート等)と
  送信が止まったまま戻らない**(プロセスは生きている)。受信ゼロのときはまず mock を
  再起動する(2026-09-08 に 2 回。修正はアプリ側リポジトリの課題)。
- M7_CORE 版 DT のクリーンブート(OTA 後、手動操作なし)で remoteproc start → rpmsgcan0 →
  実バス受信(930 フレーム/5s)まで再確認済み。
- 次段: 8MM と同じ falcon 統合(SPL が M7 ファームを検証してステージング、BL31 が起動)、
  kmm 側の CAN ソース切替の確認、Zephyr 側ログ文字列の名前整理。

## falcon 統合 — BL31 から M7 を起動する(実機で can-gw まで動作確認済み)

falcon(SPL→BL31→カーネル直行、U-Boot proper を飛ばす)で M7 を Linux より先に起こす。
8MM の SPL loadable + BL31 起動(kas/imx8mm-m4.yml)の 8MP 移植。有効化は `kas/imx8mp-m7.yml`。

**経路**: SPL(0007-imx8mp-debix-spl-m7-file-read)が BOOTA の `m7-fw.img`(magic M7FW、
falcon-itb.bb が m7-fw.bin を包む)を検証して DDR 0x46000000 にステージング → BL31
(0001-imx8mp-bl31-start-m7)が ITCM(0x7E0000)へコピーし CPUWAIT を落として M7 起動 →
Linux は稼働中 M7 に attach(imx_rproc、SIP STARTED)→ rpmsg-can が rpmsgcan0 を生やす(Linux 側の FlexCAN2 は can0 のまま。kmm は `CAN_INTERFACE=rpmsgcan0` で rpmsg 側を読む)。
実機確認: rpmsgcan0 で外部 CAN(can-mock 0x5F0〜0x5F4)を受信、rx_packets 増加。

### falcon は「U-Boot proper が立てていたもの」が立たない — 3 つの落とし穴

remoteproc 経路(Linux が M7 を起動)では U-Boot proper / Linux が立てていた初期化が、
falcon では誰も行わない。以下は全て実機で真因を確定し、修正済み。

**1. M7 ルートクロック(BL31 側)** — TCM アクセスの前提。
M7 の TCM は M7 ルートクロック(CCM `0x30388080`)が **enable(bit28)かつ稼働ソース
(mux[26:24]=1 = sys_pll2_200m)= `0x11000000`** で回っていないと死んだ AXI スレーブになり、
A53 が書くとバスでハングする。BL31 に「M7 を release せず TCM に書いて読み戻す」非致命
probe を仕込み UUU RAM 起動(eMMC 非破壊)で実測:
- `0x11000000`: 1 word write + flush + invalidate + HW 読み戻し成功、128KB fill+flush 完走。
  **EL3 でも TCM に完全に書ける**。
- `0x00000000`(disable): TCM write で即ハング。
- `0x10000000`(enable + mux=0 既定)もハング(mux=0 の源が動いていない)。
「EL3 では TCM 不可」「RDC/TZASC/MRC のアクセス制御」「BL31 の TCM ページ属性
(cacheable)」は全て**無罪**(RDC MRC region 22-26 は実測 reset 値=保護なし、TZASC は
DRAM 専用、128KB flush も通る)。sys_pll2 は SPL clock_init が出力を enable 済み(falcon でも有効)。
→ start_m7 はコピー前に `0x11000000` を書く。**enable/mux 変更直後に TCM へ書くと
クロック未安定でハングする**ため、read-back で posted write を確定させ `udelay(100)` で
安定を待ってからコピーする(実測: 各ステップに診断 NOTICE を入れた版は UART 出力が暗黙の
ディレイになって動き、NOTICE を外した版はハングした。明示ディレイ無しの本番化は不可)。
また stock の bl31_platform_setup は start_m7 の手前で M7 reset を解除するため、その前
(imx_gpc_init 直後)に CPUWAIT を立てて空 ITCM からの暴走を防ぐ。

**2. CAN1 クロック root(M7 firmware 側)** — can-gw の FlexCAN が動く前提。
M7 firmware(data-logger-zephyr apps/can-gw `kart_m7_clocks_enable`)は元々 CCGR ゲートだけ
立て、CAN1 クロック *root* は「U-Boot が立てた 24MHz osc」前提だった。falcon では root が
未 enable(CCM `0x3038a200` = `0x00000000`)のまま → Zephyr の ccm get_rate は 24MHz を返す
のに実クロック 0Hz → FlexCAN は健全に見えて(started=1, state=ERROR_ACTIVE, err=0)バス活動
をゼロ観測(can0 RX=0)。→ M7 firmware で root に `0x10000000`(bit28 enable + mux=0
osc_24m + div=0)を書く。CCGR だけでは不足。

**3. Linux の clk_disable_unused** — M-core 占有クロックの保護。
Linux 側 flexcan1 は M7 譲渡で disabled = can1 クロックに Linux コンシューマが無い。
`clk_disable_unused`(late_initcall)が M7 が立てた CAN1 root を「未使用」として無効化する
(clk_summary: can1 enable_cnt=0、root が 0 に戻る)。remoteproc 経路では Linux 自身が
M7 起動のコンシューマなので起きない。→ `kas/imx8mp-m7.yml` が **`UBOOT_EXTLINUX_KERNEL_ARGS` に
`clk_ignore_unused` を付ける**(falcon.itb の bootargs も同変数を共有)。
**falcon だけに付けると不十分**(2026-09-11 実測): SPL は `upgrade_available=1`(OTA 試行ブート)
やフォールバックで proper/extlinux 経路に落ち、extlinux の APPEND に引数が無いと Linux が
CAN1 root を 0 に落として M7 が `set_bitrate` で FlexCAN を叩いた瞬間に固まる(RAM console が
`can` で途切れる)。`fw_setenv upgrade_available 1; reboot` で 1/1 再現、両経路に付けて解消
(OTA tryboot の起動で `started=1`、`0x3038a200=0x10000000`)。通常の warm reboot(falcon)は
10/10 正常。

### 運用上の要点(falcon で BL31/M7 を差し替えるとき)
- **falcon 起動で走る BL31 は `falcon.itb`(BOOTA)内のもの**。`imx-boot`(flash.bin)の BL31
  は falcon では使われない。BL31 を変えたら falcon.itb を焼く(full-image OTA なら自動)。
- **falcon 経路になるのは `boot_os=yes`(SPL ログ `bos=1`)のときだけ**。デッドマンで
  `bos=0` になると proper へフォールバックするが、falcon SPL は proper に到達できず
  ハングする(kas/imx8mp-falcon.yml 注記)。起動失敗の連鎖は boot_os を確認する。
- 外部 CAN 送信側(CANable/can-mock)は、M7 が無応答だった期間に ACK 無しで bus-off に
  陥り送信を止めることがある。M7 復旧後は送信側を再起動する。

### デバッグの道具
- **M7 の RAM console は Linux から読める**: `/sys/kernel/debug/remoteproc/remoteproc0/trace0`
  (resource table の trace エントリ)。`can-gw: start rc=`、`started/state/rx_err`、
  `can->rp/rp->can` カウンタで M7 側の状態が分かる。
- BL31 の実験は UUU `SDPS: boot -f <非 falcon imx-boot>` で RAM 起動すれば eMMC 非破壊
  (falcon SPL は SDPV に非対応なので RAM 起動には非 falcon ビルドを使う)。
- CCM 実値は Linux の devmem で確認できる(M7 root `0x30388080`、CAN1 root `0x3038a200`、
  CAN1 CCGR `0x30384350`)。flexcan1 レジスタは M7 ドメインで A53 から読めない。
- ブートモード/電源/シリアルの遠隔操作は [[debix-boot-switch]]、eMMC 復旧は
  [[debix-emmc-recovery-via-uboot]]。
